## 13.1 实战案例：企业飞书群工作助手

### 13.1.1 问题定义与场景约束

一个 30 人规模的工程团队日常通过飞书（Lark）协作，希望在群里有一个智能助手，具备以下能力：

- 回答关于内部文档和代码仓库的问题
- 总结每日 GitHub PR 活动
- 通过自然语言创建和查询 Jira 工单
- 根据用户角色实施权限控制（工程师 vs 访客）

约束条件：必须在现有飞书群内运行，无需新增基础设施（仅通过 OpenClaw Gateway）。

### 13.1.2 最小闭环：单工具单渠道跑通

先按[第七章 7.2 飞书接入指南](../07_multi_agent/7.2_lark_integration.md)打通私聊。本例使用团队专属测试实例，唯一的智能体为 `main`，已配置模型与记忆检索服务。把一份允许群成员阅读的文档放入该智能体工作区的 `memory/` 目录。比如在 `memory/team-help.md` 中写入“测试项目的工单前缀为 ORBIT”。

将以下字段合入已有的 `openclaw.json`，保留向导生成的渠道账户、凭据和模型设置。用测试群的实际 `chat_id` 替换 `oc_xxx`；如果账户单独设置过群策略，请在该账户下设置相同的允许名单。单智能体实例会把允许的群消息交给 `main`。[飞书群访问控制](https://docs.openclaw.ai/channels/feishu/access-control) · [智能体路由](https://docs.openclaw.ai/concepts/multi-agent)

```json
{
  "agents": {
    "entries": {
      "main": {
        "tools": { "allow": ["memory_search"] }
      }
    }
  },
  "channels": {
    "feishu": {
      "groupPolicy": "allowlist",
      "groupAllowFrom": ["oc_xxx"],
      "requireMention": true
    }
  }
}
```

先检查配置并验证文档能被检索：

```bash
openclaw config validate
openclaw memory index --agent main
openclaw memory search --agent main "测试项目的工单前缀"
```

检索应返回包含 `ORBIT` 的文档片段。确认已运行的 Gateway 载入配置后，在允许的群内 @ 机器人，要求它“搜索团队文档，给出测试项目的工单前缀”。检查工具记录里有一次 `memory_search` 命中，并在群中核对答案。本例使用自动回复模式；如果实例要求显式调用 `message` 才能发送群消息，需另行允许该工具。

### 13.1.3 关键配置拆解

在知识库检索通过后，再接入业务插件并限制调用范围。

#### 1. 增加工具：GitHub PR 分析与 Jira 工单管理

先安装并配置团队自己的业务插件，记下它们实际注册的工具名。面向真实群开放前，应先落实下一节的角色授权，确保访客无法执行工单写入。假设分别注册为 `github_pr_analyzer` 和 `jira_issue_manager`，将下列片段合入 `agents.entries.main`。仅添加名称不会创建工具或配置服务凭据。

```json
{
  "tools": {
    "allow": ["memory_search", "github_pr_analyzer", "jira_issue_manager"]
  }
}
```

详见[第五章 工具入门](../05_tools_skills/README.md)。

#### 2. 添加权限控制：基于角色的访问策略

角色权限不要写成顶层 `profiles` / `guardrails` 的旧 schema。更稳妥的做法是把“工程师 vs 访客”的差异映射到渠道 sender 策略、agent 工具 allowlist 或 hook。下面只表达授权矩阵：

```text
engineer: memory_search, github_pr_analyzer, jira_issue_manager
guest:    memory_search
```

落地时要区分渠道能力：Slack 可使用 channel / group 层的 `toolsBySender` 为工程师账号 `alsoAllow` 高权限工具；Feishu 当前应先用 `channels.feishu.groupSenderAllowFrom` 或 `groups.<chat_id>.allowFrom` 控制谁能触发群机器人，再用 `groups.<chat_id>.tools` 控制群级工具集合。Feishu sender-specific 高风险授权更适合放在全局/agent 工具策略或 `before_tool_call` hook 中，按 sender、群 ID 与企业目录查询结果做动态拒绝。详见[第五章 5.2 工具策略](../05_tools_skills/5.2_tool_policy.md)与[第十一章 11.4 防护栏](../11_reliability_security/11.4_guardrails.md)。

#### 3. 添加定时任务：每日 PR 摘要

“每日 PR 摘要”这类任务在当前版本中应优先映射到 Gateway 的 Cron 作业。下面的内容只表达**作业意图**，不再把 `cron_tasks` 写成现行配置字段：

```json
{
  "job_spec_example": {
    "daily_pr_summary": {
      "schedule": "0 16 * * *",
      "agent": "main",
      "tool": "github_pr_analyzer",
      "channel": "feishu",
      "instruction": "生成过去 24 小时的 PR 活动摘要，列出：1) 新开的 PR 数量、2) 已合并的 PR 数量、3) 待审核 PR 列表。用简洁的 Markdown 格式。",
      "timezone": "Asia/Shanghai"
    }
  }
}
```

这会在每天下午 16:00（由 `timezone: "Asia/Shanghai"` 指定为北京时间）触发 PR 摘要任务；若使用 CLI 创建同类 cron，应显式传入 `--tz Asia/Shanghai`，否则会按 Gateway 主机时区解释。若要投递到飞书群，需要显式配置 delivery/announce、`channel: "feishu"` 和目标群 `to: "<feishu-chat-id>"`，或在任务中调用 `message(action=send)`。详见[第八章 自动化与定时任务](../08_automation_ops/README.md)。

### 13.1.4 验收清单与常见失败点

逐项验证配置的正确性：

1. **机器人处理群消息** → 在飞书群中 @ 机器人或按 group policy 触发，确认日志中有 agent turn；若需要房间可见回复，确认作业或工具显式投递到群里
2. **知识库搜索有结果** → 提问一个文档中确实存在的问题（例如“API 文档在哪里”），确认搜索返回相关内容
3. **权限控制生效** → 用访客账户在群里发送“请分析最近的 PR”，验证机器人回复“您没有权限使用此功能”或类似拒绝提示
4. **定时任务正常触发** → 检查日志确认任务在预期时间（北京时间 16:00）执行

常见失败及排查方案：

| 问题 | 可能原因 | 排查步骤 |
|------|--------|--------|
| “机器人不回复” | 飞书应用权限、事件订阅顺序、渠道配置字段与当前版本不匹配 | 查看[第七章 7.2](../07_multi_agent/7.2_lark_integration.md)“防坑预警”；优先对照当前 `config.schema` 与 Dashboard Config 页，而不是直接照抄旧字段 |
| “知识库没有结果” | OpenClaw memory 索引未写入，或自定义检索插件配置与实际暴露路径不一致 | 在同一智能体上运行 `openclaw memory search --agent main` 并附上原问题；若搜不到文档，检查工作区、索引和 embedding 配置 |
| “访客仍能调用高权限工具” | `toolsBySender`、工具策略或自定义 hook 未命中 | 用 `openclaw sandbox explain` 检查有效工具策略；条件化访问应放在 `toolsBySender` 或 `before_tool_call` hook 中，不要把 `condition` 写进 `tools.deny` |
| “定时任务不执行” | 时区配置错误或 cron 表达式语法错误 | 检查 `timezone` 字段是否为有效的 IANA 时区名称（如 `Asia/Shanghai`）；验证 `schedule` 是标准 5 字段 cron 格式 |

### 13.1.5 扩展到生产时再加什么

从测试环境迁移到生产时，需要补充以下几个方面（配置细节参见相应章节）：

**Kubernetes 部署** - 不再用 `openclaw gateway start` 本地运行，而是部署成 Pod，支持多副本和自动扩展。详见[第十二章 12.4 生产落地蓝图](../12_extension_engineering/12.4_production_blueprint.md)。

**监控和告警** - 接入 Prometheus 或 DataDog 监控机器人的响应时间、错误率、工具调用频率。详见[第十二章 12.4.5 监控与告警](../12_extension_engineering/12.4_production_blueprint.md)。

**多渠道支持** - 同时接入 Slack、Discord、Telegram、WhatsApp、Feishu/Lark 等渠道时，以官方 README、channels 文档与 `channels capabilities` 输出为准，区分 bundled、downloadable/external plugin 与第三方插件。WebChat / Control UI Chat 属于 Gateway UI / 内部聊天入口，不应按普通出站渠道配置。

**审计日志** - 记录所有工具调用、用户操作和权限检查结果。详见[第十一章 11.4 防护栏](../11_reliability_security/11.4_guardrails.md)。

完整的 Kubernetes 部署配置与监控告警设置，参见[第十二章生产落地蓝图](../12_extension_engineering/12.4_production_blueprint.md)。

## 8.3 周期巡检：从 Heartbeat 到自动化作业

上一节讨论面向精确时间点的定时作业；本节讨论另一类调度需求：**周期巡检**。

设想有 5 个信息源需要定期检查（邮箱、待办、日历、Slack、监控面板）。若为每个源各写一个定时作业，就要分别维护 5 份调度、重试与日志；而这些检查大多没有新内容，只会白白消耗 API token。更合适的做法是：按固定间隔运行一次智能体，按一份检查清单逐一扫描这些源，只有存在需要关注的事项时才发送通知。

OpenClaw 早期用独立的 Heartbeat（心跳）运行器承担这一职责。当前版本已撤销该运行器：周期巡检就是一个普通的自动化作业（[8.2 节](8.2_cron_jobs.md)的 `openclaw automations`），它的调度、提示词、检查清单、模型、会话和投递设置都随作业保存，可以像其他作业一样查看、编辑、停用和删除。`agents.defaults.heartbeat`、`agents.entries.*.heartbeat` 与渠道的 `heartbeatVisibility` 只作为 `openclaw doctor --fix` 的迁移输入，留在配置中会使配置校验失败。参考：[Heartbeat migration](https://docs.openclaw.ai/gateway/heartbeat)。

> [!TIP]
> 快速判断：需要精确时间 → `--cron` / `--at` 作业；需要周期性感知、有变化才通知 → `--every` 巡检作业。二者都是自动化作业，区别在调度方式、会话与静默策略，详见 8.3.6。

### 8.3.1 巡检作业的组成

一个巡检作业由以下几部分构成：

- **调度**：通常用 `--every 30m` 这类固定间隔。
- **提示词**：`--message` 写明要检查什么、什么情况算“需要关注”，以及无事时回复 `NO_REPLY`。
- **scratch**：附在作业上的私有上下文，相当于检查清单，每次运行时注入；它取代了工作区里的 `HEARTBEAT.md`。
- **监控策略**：活跃时段（`activeHours`）、前台优先（`idleOnly`）和空清单跳过（`skipIfScratchEmpty`）。
- **投递**：结果发到渠道、webhook 或不外发；无事时静默。

显式执行初始设置时，OpenClaw 会为默认（ambient owner）智能体创建一个名为 **Proactive check** 的巡检作业：每 30 分钟运行一次（供应商另行给出初始间隔时除外），使用该智能体的主会话，等待空闲后执行，结果投递到已识别的所有者私聊；scratch 被显式清空时跳过，scratch 不存在时照常运行。这个作业只创建一次，Gateway 启动和配置重载都不会重建它，删除即为长期选择；其他智能体需要各自显式创建作业。

### 8.3.2 迁移旧的 Heartbeat 配置

升级到当前版本后，先运行迁移，再查看全部作业（含已停用的）：

```bash
openclaw doctor --fix
openclaw automations list --all
```

Doctor 把每个旧监控转换为普通的可编辑作业，保留其身份、运行历史、scratch 及其修订记录、停用状态、调度锚点与待执行的时间槽；受支持的 `HEARTBEAT.md` 内容和任务块会被导入 scratch，原文件归档到状态目录下的 `backups/heartbeat-migration/`。旧的心跳配置只有在对应作业写入并校验通过后才会被移除；转换受阻时，诊断信息会指出剩余的输入，应修复后重新运行 Doctor，而不是手动删除配置。Doctor 只支持 2026 年 7 月及之后版本的心跳配置形态。

字段的去向如下：

| 旧配置 | 迁移后 |
|--------|--------|
| `heartbeat.every` | 作业调度（`--every`） |
| `heartbeat.prompt` | 作业提示词（`--message`）；单独一行的 `HEARTBEAT_OK` 改为 `NO_REPLY` |
| `HEARTBEAT.md` | 作业 scratch（`openclaw automations scratch`） |
| `heartbeat.activeHours` | 作业 `activeHours`（`--active-hours-*`） |
| `heartbeat.model` | 作业模型覆盖（`--model`）；不在该智能体 `modelPolicy.allow` 内的模型会被丢弃并报告 |
| `heartbeat.target` / `to` / `accountId` | 作业投递（`--announce --channel --to --account`） |
| `heartbeat.directPolicy` | `delivery.directPolicy`（`--direct-policy`） |
| `channels.*.heartbeatVisibility` | 普通自动化投递：有结果时投递，`NO_REPLY` 时静默 |

迁移后的投递按普通作业语义处理：心跳特有的重复内容去重和“无投递路由即跳过”都已移除，重复的更新可能再次投递，缺少路由也不会在执行前跳过本次运行。依赖这两种行为的作业，迁移后应检查投递设置。

> [!WARNING]
> 迁移会把共享状态数据库升级到 schema 30，旧版 Gateway 无法再运行这些作业。升级前应保留经过验证的备份；需要回滚时，把升级前的备份恢复到另一个状态目录，不要手动降低 schema 版本号。

### 8.3.3 创建与管理巡检作业

下面创建一个工作时段内每 30 分钟运行一次的巡检作业，结果投递到所有者的 Telegram 私聊：

```bash
openclaw automations add \
  --name "收件箱与日历巡检" \
  --every 30m \
  --session isolated \
  --message "检查本作业 scratch 中列出的信息源，只报告需要处理的变化；没有变化时回复 NO_REPLY。" \
  --active-hours-start 09:00 \
  --active-hours-end 22:00 \
  --active-hours-timezone user \
  --idle-only \
  --skip-if-scratch-empty \
  --announce --channel telegram --delivery-target owner
```

`--delivery-target owner` 在投递时解析已明确识别的所有者私聊；它不会像 `channel: "last"` 那样跟随最近的群聊，所有者身份不明确时也不会猜测收件人。`--direct-policy allow|block` 控制是否允许投递到私聊。

日常管理与其他作业相同：

```bash
openclaw automations show <job-id>
openclaw automations edit <job-id> --message "只报告新出现的阻塞项；没有变化时回复 NO_REPLY。"
openclaw automations runs <job-id>
openclaw automations disable <job-id>
openclaw automations remove <job-id>
```

### 8.3.4 检查清单与活跃时段

#### scratch：作业的检查清单

scratch 保存在共享状态数据库中，每次运行时作为有界上下文注入作业：

```bash
openclaw automations scratch <job-id> --set "检查收件箱中的紧急邮件、未来 2 小时的日历事件，以及已完成的后台任务；只报告需要处理的变化。"
openclaw automations scratch <job-id>
openclaw automations scratch <job-id> --unset
```

设计要点：

- **保持精简。** scratch 会进入每次运行的提示词，清单越长，token 成本越高。
- **区分“空”与“不存在”。** 启用 `--skip-if-scratch-empty` 后，只含空白、注释、标题、代码围栏或空复选框的 scratch 视为空，本次运行跳过；没有 scratch 时照常运行。
- **智能体可以维护自己的清单。** 作业运行期间，智能体可通过 `automations` 工具读写本作业的 scratch（`scratch_get` / `scratch_set`），但不能访问其他作业。写入按修订号做比较交换，CLI 可用 `--expected-revision <n>` 固定修订。
- **scratch 不是调度器。** 运行时不会把其中的 `tasks:` 块解析成调度，也不再读取 `HEARTBEAT.md`；需要不同节奏的检查应拆成独立作业。
- **不要放敏感信息。** scratch 存储私有，但仍会进入模型提示词。

#### 活跃时段与前台优先

`activeHours` 按时区限制执行窗口，起点包含、终点不包含，支持跨午夜：

| 目标 | 配置 |
|------|------|
| 工作时间才巡检 | `--active-hours-start 09:00 --active-hours-end 18:00` |
| 全天候运行 | 不设活跃时段（默认） |
| 避免深夜打扰 | `--active-hours-start 08:00 --active-hours-end 24:00` |

时间格式为 `HH:MM`，只有终点可以写 `24:00`。`--active-hours-timezone` 可取 `user`（默认，使用配置的用户时区）、`local`（Gateway 主机时区）或 IANA 时区。周期作业落在窗口外的那一次会被跳过，直接推进到下一个调度点；一次性 `--at` 作业则等到窗口打开再执行。手动强制运行会绕过调度节奏，但仍受活跃时段约束。

> [!WARNING]
> 起点和终点相同（如 `08:00` 到 `08:00`）定义的是空窗口，作业将永远不会执行。

`--idle-only` 让前台工作优先：作业等待空闲时不占用运行槽位。

### 8.3.5 静默结果与投递

巡检作业的核心约定是“有事才通知”：

- **无事发生**：最终回复 `NO_REPLY`，文本类投递被抑制，本次运行仍记为成功。
- **有事需要关注**：正常回复，按作业的投递设置（`--announce` 发到渠道、`--webhook` 发到 URL、`--no-deliver` 不外发）处理。
- **结构化结果**：运行期间可用 `automations` 工具的 `record_result` 记录 `no_change`、`progress`、`done`、`blocked` 或 `needs_attention`。它只记录、不发送；除 `no_change` 外都需要附 1–2000 字符的摘要。最近一次有意义的结果会作为有界上下文带入下一次运行。

迁移来的提示词或告警中若仍出现位于开头或结尾的 `HEARTBEAT_OK`，投递时会被剥离，告警正文的换行、列表和代码块保持原样。

`openclaw automations show` 把有意抑制的成功运行标为 `ok (suppressed)`，并给出抑制原因（`empty`、`silent`、`heartbeat` 或 `channel_transform`）；真正的投递失败显示为 `ok (not delivered)`。排查“作业跑了但没收到消息”时，先用 `openclaw automations runs <job-id> --delivery-status not-delivered` 筛出未投递的运行。

### 8.3.6 即时跟进与系统事件

后台进程结束、任务进入阻塞、重启完成这类跟进，走普通会话执行，不需要启用周期巡检作业；会话准入会把跟进留在原会话中，并沿用当前权限。需要手动触发时，显式要求立即处理：

```bash
openclaw system event --text "检查是否有紧急的跟进项" --mode now
```

兼容用法的行为如下：

- `--mode next-heartbeat`：把事件挂到该会话中一个符合条件的已调度作业上；找不到时直接报告问题，而不是等待某条不确定的后续消息。延后的工作应优先用显式调度表达。
- `openclaw automations add` 的 `--wake now|next-heartbeat` 已弃用：仍被接受，但作业到期时就按普通会话执行，不再附加唤醒或延后步骤。
- `set-heartbeats` 只启停迁移来的或默认创建的巡检作业，不影响其他作业；`last-heartbeat` 保留兼容的事件响应。

连接保活、在线状态等基础设施健康信号与智能体巡检无关，仍按各自的配置工作（WebSocket 保活见 [9.3 节](../09_gateway_protocol/9.3_ws_handshake.md)）。

### 8.3.7 选型：巡检作业与定点作业

周期巡检与定点作业都是自动化作业，选型落在三个问题上：何时运行、在哪个会话运行、无事时是否静默。

```text
需要在精确时间点运行？
  是 → --cron（周期）或 --at（一次性），配合 --tz
  否 → --every 巡检作业，提示词约定无事回复 NO_REPLY

需要主会话的完整上下文？
  是 → --session main
  否 → 继续…

需要跨次运行积累上下文？
  是 → --session session:<id>
  否 → --session isolated（每次全新会话）

需要不同的模型或思考深度？
  是 → --model / --thinking（模型须在该智能体允许的范围内）
```

四种会话方式的差异：

| 方式 | `--session` | 运行位置 | 适用场景 |
|------|-------------|---------|---------|
| 主会话 | `main` | 所属智能体的主会话，沿用其上下文与投递上下文 | 提醒、系统事件 |
| 隔离 | `isolated` | 专用 `cron:<jobId>` 会话，每次全新 | 报告、后台杂务、多数巡检 |
| 当前会话 | `current` | 创建作业的会话的子运行，读取该会话的有界尾部 | 依赖上下文的周期工作 |
| 自定义会话 | `session:<id>` | 持久的具名会话 | 在历史结果上累积的工作流 |

**建议把多项检查合并进一个巡检作业。** 一个作业一次运行完成收件箱、日历、通知等多项检查；需要精确时间的独立任务（日报、周会回顾、定点提醒）另建定点作业。这样既减少模型调用次数，又保证关键作业的时间精度。

#### 成本控制建议

巡检作业每次运行都是一次完整的智能体回合，不加控制时 token 消耗可观。降本手段包括：

- **精简 scratch**：清单越短，每次注入的 token 越少。
- **使用 `--light-context`**：跳过工作区引导文件的注入。
- **使用便宜的模型**：通过 `--model` 为巡检作业指定更经济的模型，核心对话仍用高端模型。
- **启用 `--skip-if-scratch-empty`**：清单被清空时直接跳过本次运行。
- **用确定性条件先过滤**：能用脚本判断的条件（如文件是否变化），交给作业的条件触发器决定是否运行，不必为“确认没变化”付一次模型调用。
- **拉长间隔、限制活跃时段**：把 `--every` 调到 `1h` 或更长，并在夜间跳过运行。
- **只需内部记录时用 `--no-deliver`**：不外发结果，只保留运行历史。

## 12.2 自定义工具的设计与治理

自定义工具的难点不在于写一个函数，而在于把副作用做成可控、可审计、可回滚的工程能力。在 OpenClaw 中，插件负责引入工具能力，工具策略负责收敛可执行边界，多智能体与沙箱工具负责把高风险动作隔离在受控执行域。本节讨论工具扩展的落地方法，重点是配置层面的确定性约束与可验证的验收路径。

### 12.2.1 自定义工具的最小原则：输入可验证，输出可回放

将工具纳入系统之前，应先明确三项契约：

1. 输入约束：参数必须可验证，避免把“自由文本”直接作为高风险工具参数。
2. 输出约束：输出必须结构化，避免回注导致上下文膨胀。
3. 副作用边界：写操作必须具备幂等或对账路径，失败时必须给出人工核查步骤。

这些约束不依赖模型能力，是工具设计的确定性底线。

#### 工具设计的常见反例

以下三个反例说明上述约束缺一不可：

**反例一：把自由文本直接拼进 SQL 查询**

某个数据导出工具接受用户提供的表名作为参数，不做校验就直接嵌入 SQL 查询字符串，攻击者可以注入 `; DROP TABLE users; --` 造成数据丢失。“输入可验证”约束要求参数必须通过白名单或正则模式验证，不允许自由文本直接参与高风险操作。

**反例二：工具输出未结构化，回注导致上下文膨胀**

某个日志查询工具输出整个日志文件的原始内容，模型无法解析，只能通过多轮补全请求理解结果，最终上下文中充斥大量冗余日志，后续推理变慢且容易出错。“输出结构化”约束要求工具预先过滤与聚合，只返回关键字段，例如：`{ "error_count": 5, "latest_error": "...", "affected_services": [...] }`。

**反例三：写操作缺乏幂等键，重试导致重复创建**

某个工单创建工具没有实现去重逻辑，网络超时导致重试时，系统会多次创建相同的工单。即使模型检测到重复，也无法自动回滚，最终需要人工清理。“副作用可回滚”约束要求写操作必须支持幂等键（如请求 ID）或显式提供回滚步骤（如“删除工单 ID 10001”）。

### 12.2.2 把工具接入工具策略：分层规则与拒绝优先

工具治理应落在工具策略层。官方文档给出了工具的允许、拒绝与按渠道/群组分层限制机制，并强调拒绝规则优先：[https://docs.openclaw.ai/tools](https://docs.openclaw.ai/tools)。

下例是一种常见写法：全局先禁止宿主机运行时工具，再按入口决定是否进一步收紧文件写能力。不要把某个工具放进全局 `deny` 后，再指望后续的 `toolsBySender` 将其恢复，因为拒绝规则优先。

```javascript
{
  tools: {
    profile: 'coding',
    deny: ['group:runtime'],
  },
  channels: {
    telegram: {
      groups: {
        '*': {
          tools: { deny: ['write', 'edit', 'apply_patch'] },
        },
      },
    },
    discord: {
      groups: {
        ops: {
          tools: { deny: ['group:runtime'] },
        },
      },
    },
  },
}
```

这样，Telegram 群入口只能读取和检索，Discord 的 `ops` 组仍可使用 `coding` profile 中未被拒绝的文件写工具，两类入口都不能调用宿主机运行时工具。某个请求触发写工具而被拒绝时，日志应给出明确的拒绝原因，便于追溯是策略拒绝还是参数不合法。

#### 工具注册的 TypeScript 签名

OpenClaw 插件用 TypeScript 注册工具。常见写法是注册 tool object；需要运行时上下文或延迟构造时，也可以注册 tool factory。参数 schema 通常使用 `Type.Object()`（基于 TypeBox，一个用于生成 JSON Schema 的类型构建库），执行逻辑由 `execute(id, params)` 方法实现。下例是一个符合官方签名的工具注册流程，包含参数约束、错误处理与结构化返回：

```typescript
import { Type } from "@sinclair/typebox";

api.registerTool({
  name: "create_ticket",
  description: "Create a support ticket with validation",
  parameters: Type.Object({
    title: Type.String({ minLength: 5, maxLength: 200 }),
    category: Type.Union([
      Type.Literal("bug"),
      Type.Literal("feature"),
      Type.Literal("ops"),
    ]),
    priority: Type.Number({ minimum: 1, maximum: 5 }),
    assignee_id: Type.String({ pattern: "^[0-9a-f]+$" }),
  }),
  async execute(id, params) {
    // 执行层（带错误处理）
    try {
      const ticket = await ticketService.create({
        title: params.title,
        category: params.category,
        priority: params.priority,
        assignee_id: params.assignee_id,
        idempotency_key: id, // 用工具调用 ID 作为幂等键
      });

      // 结构化返回
      return {
        content: [{ type: "text", text: `Ticket ${ticket.id} created` }],
        details: {
          ticketId: ticket.id,
          status: ticket.status,
          createdAt: ticket.createdAt,
        },
      };
    } catch (err) {
      return { content: [{ type: "text", text: "internal error" }] };
    }
  },
});
```

关键点：(1) 参数 schema 用 TypeBox 的 `Type.Object()` 声明，由框架在调用前自动校验，无须在 execute 中重复验证；(2) `execute(id, params)` 的 `id` 是框架分配的调用标识，可直接用作幂等键；(3) 返回值遵循 `AgentToolResult`，面向模型的内容放在 `content`，结构化追踪字段放在 `details`，不要把 `success` 视为必需顶层字段；(4) 每个 `api.registerTool(...)` 注册的工具还必须在 `openclaw.plugin.json` 的 `contracts.tools` 中声明；可选工具需要注册时传 `{ optional: true }`，并同时设置 `toolMetadata.<tool>.optional: true`。

### 12.2.3 工具版本管理与生命周期

生产环境的工具不能无限制地迭代，需要建立明确的版本管理与弃用策略，保证已部署智能体的行为不因工具变更而失效。

OpenClaw 官方目前未内置工具版本管理机制，团队可以用以下工程实践自行管理工具的演进与弃用：

1. 在工具定义中声明向后兼容性。参数、返回值或行为变化时，明确标记是否兼容。
2. 弃用期设置在 180 天以上。某个工具版本进入弃用期时，应显式警告并给出升级窗口。
3. 记录工具调用链路上的版本号，便于追溯行为差异。

下面是一种团队自行维护的版本追踪方案示例（非官方配置格式，仅作工程参考）：

```javascript
// 团队内部的工具版本追踪文件（如 tool-versions.json），用于文档化管理
{
  tools: [
    {
      id: 'query_database',
      versions: {
        '1.0': {
          status: 'deprecated',
          params: ['query', 'timeout'],
          deprecatedAt: '2026-01-15',
          sunsetsAt: '2026-07-15',
          migrateToVersion: '1.1',
        },
        '1.1': {
          status: 'active',
          params: ['query', 'timeout', 'schema'],
        },
      },
    },
  ],
}
```

在工具调用日志中记录所选版本，便于判断行为不一致是否由版本差异导致：

```bash
openclaw logs --follow --json | jq -c 'select(.type=="log") | (.raw | fromjson? // {}) as $raw | select(($raw|tostring)|contains("query_database")) | {time, level, subsystem, raw:$raw}'
```

当前工具策略按工具名、glob 或分组匹配，不解析内置的 `tool@version` 语法。需要版本级策略时，应把版本编码进不同的工具名或插件配置，再用现有工具策略控制允许与拒绝。

### 12.2.4 工具组合与编排：多工具协作的确定性约束

单个工具的幂等性保证不足以应对复杂任务。多个工具协作时，工具之间的依赖关系、执行顺序与数据流必须显式声明，不能依赖模型的“推理”。

定义工具编排脚本时，建议采用声明式依赖图：

1. 显式声明工具调用的前置条件与后置验证。
2. 工具输出必须经过验证才能作为下一工具的输入。
3. 失败原子性：某工具失败时的回滚路径必须预先计划。

> [!NOTE]
> 下面是团队自定义编排层的伪配置，用于说明依赖图设计，不是当前 OpenClaw 的内置 schema。需要运行时编排时，优先参考当前 Task Flow / Lobster 等官方能力，或在插件中实现自己的工作流执行器。

```javascript
{
  tools: {
    orchestration: {
      workflows: [
        {
          id: 'deploy_service',
          steps: [
            {
              tool: 'validate_config',
              params: { config_path: '/config.yaml' },
              required: true,
              onFailure: 'abort',
            },
            {
              tool: 'build_image',
              params: { source: '/src', tag: 'service:latest' },
              requires: ['validate_config'],
              requiredOutputSchema: { passed: 'boolean' },
            },
            {
              tool: 'push_registry',
              params: { image: 'service:latest', registry: 'internal' },
              requires: ['build_image'],
              requiredOutputSchema: { imageId: 'string' },
            },
            {
              tool: 'deploy_canary',
              params: { image: 'service:latest', replicas: 1 },
              requires: ['push_registry'],
              onFailure: 'rollback_to:previous_image',
            },
          ],
        },
      ],
    },
  },
}
```

工具编排执行时，每一步的输入输出都应记录在日志中，便于后续重放与定位：

```bash
openclaw logs --follow --json | jq -c 'select(.type=="log") | (.raw | fromjson? // {}) as $raw | select(($raw|tostring)|contains("deploy_service")) | {time, level, subsystem, message, raw:$raw}'
```

### 12.2.5 高风险工具的隔离执行：多智能体沙箱工具

涉及代码执行、文件写入或系统操作的高风险工具，建议配合多智能体沙箱工具隔离执行域。官方文档给出了沙箱工具的能力边界与认证配置，并指出认证配置文件位于 `~/.openclaw/agents/<agentId>/agent/auth-profiles.json`：[https://docs.openclaw.ai/tools/multi-agent-sandbox-tools](https://docs.openclaw.ai/tools/multi-agent-sandbox-tools)。

工程上建议采用“少数智能体拥有写能力”的模式：

1. 大多数入口智能体只允许读工具与诊断命令。
2. 少数运维智能体在明确入口与审计前提下允许沙箱写工具。

这一模式与第 7 章的入口绑定与路由策略配合使用，可以把越权风险收敛到可计算的范围。

#### 沙箱工具的认证配置

沙箱工具执行高风险操作时必须基于明确的认证身份。认证配置文件 `~/.openclaw/agents/<agentId>/agent/auth-profiles.json` 定义沙箱环境中可用的认证凭证与权限边界，保证写工具只能在授权范围内执行。例如，可以为某个运维智能体配置 SSH 密钥或 API Token，使其只能操作指定的基础设施资源，读工具则不受认证限制。这种认证隔离与前述工具策略的拒绝规则配合，形成多层防御。

### 12.2.6 验收与排障：先看策略加载，再看单次调用链

自定义工具上线后的验收建议固定为两步：

1. 配置验收：用 `openclaw config get tools --json` 和对应渠道配置路径确认声明式策略已加载，再用 `openclaw sandbox explain --agent <id> --json` 查看实际沙箱/工具策略。
2. 行为验收：用结构化日志观察工具调用与拒绝事件，确保拒绝规则生效。

```bash
openclaw config get tools --json
openclaw sandbox explain --agent <id> --json
openclaw logs --follow --json
```

发现工具被误允许时，优先回到工具策略，检查 deny 与渠道/群组级策略限制；发现工具执行失败时，先区分外部依赖故障与参数不合法，再决定是否允许有界重试。
